# 設計メモ

実運用の中で見つかった問題と、それに対してどう作ったかの記録です。
コードを読む前にここを読むと、なぜこの形になっているかが分かります。

## 前提

- 情報源は雑多で、形式が揃っていない。メール、PDF、写真、Classroomの投稿など
- **同じ予定が複数の資料に、違う言い方・違う日付で出てくる**
- 予定は後から変更される。しかも変更は「差分」ではなく、新しい資料の全文として届く
- 抽出にLLMを使う以上、結果は毎回わずかに揺れる
- 書き込む先は家族が見るカレンダーなので、壊すと実害がある

最後の2つが効いていて、「だいたい合っている」だけでは使えません。
**間違ったときに気づけること**と、**間違いを直せること**が要件になります。

## 全体の流れ

```
取得 ──→ 抽出 ──→ 整理 ──────────────→ 同期
Gmail    Claude   同一性で統合         Googleカレンダー
PDF      +確信度   食い違いを検出        新規/更新/削除候補
写真(OCR)          他クラス分を除外
手動テキスト        除外ルールを適用
```

対応するモジュール:

| 段階 | 場所 |
|---|---|
| 取得 | `sources/` — `fetch()` で `RawDocument` を返すだけの薄い層 |
| 抽出 | `extraction/llm_extractor.py`, `extraction/schema.py` |
| 整理 | `pipeline/dedup.py`, `pipeline/exclusions.py`, `pipeline/runner.py` |
| 同期 | `calendar_sync/google_calendar.py` |
| 費用 | `pipeline/cache.py`, `pipeline/usage.py` |

## 1. 予定の同一性

**これが設計の中心です。**

最初は「種別・科目・日付」で予定を識別していました。これは2つの形で壊れます。

- **提出日が変更されると別の予定になる。** 古い日付の予定がカレンダーに残ったまま、
  新しい日付に重複が現れる
- **同じ日に締め切られる別々の課題が1件に潰れる。** B-3 と B-4 が統合され、片方が
  黙って消える

そこで、抽出時に `identity_key`(課題番号や試験名など、その予定に固有の記号)を
出させ、カレンダー上の識別子をそこから作ります。日付は含めません。
提出日が動いても同じ識別子のままなので、新規登録ではなく既存の予定の更新になります。

呼び方は資料ごとに揺れます(「週末課題B-1」「長文B-1」「長文問題集のB-1」)。
そのため、キーは呼称ではなく**番号・記号を中心に**書くようプロンプトで指示し、
コード側でも NFKC 正規化・空白除去・小文字化を掛けて表記ゆれを吸収します。

### 識別子が変わったときの引き継ぎ

`identity_key` はLLMが毎回書き起こすので、**同じ予定でも文言が揺れます**。
プロンプトを改善するたびに揺れるので、これは避けられません。

そこで、予定には識別子とは別に「種別・科目・日付」から作る補助キーも保存します。
識別子で見つからないときは補助キーで探し、見つかれば同じ予定として引き継ぎます。
同じ日の別々の課題を取り違えないよう、一度使われた予定は対象外にします。

導入前の識別子でも探すので、識別方法を変えても既存の登録を削除して作り直す
必要がありません。手で編集された内容を保ったまま移行できます。

## 2. 資料どうしが食い違うとき

同じ予定について違う日付が書かれていたら、**基本は最新の資料を採用**します。
配布日/受信日が新しいほうが、更新された情報である可能性が高いためです。

ただしこれは、**新しい資料が古い情報を更新している場合にだけ**正しい判断です。
同じ配布物がクラス別・担当者別に違う日付で出されることがあり、それを「変更」と
解釈すると、他クラスの日程がそのまま登録されます。実際に起きました。

対策は2段階です。

**資料の対象を読み取る。** 抽出時に `audience`(「3,4,5組」「B先生担当クラス」など)を
出させます。1つの連絡がクラスごとに違う日程を並べている場合は、予定ごとに対象を
持たせます。

**自分のクラスと突き合わせる。**

| 状況 | 動作 |
|---|---|
| 対象がクラスの列挙で、自分のクラスが無い | 取り込まない |
| 双方の対象が判明していて食い違う | どちらも登録せず、判断を人に委ねる |
| クラス番号で書かれておらず判定できない | 取り込むが警告する |
| 学年全体・保護者全体向け | そのまま取り込む(警告もしない) |

1クラスだけのコースは、配布物にクラス番号ではなくコース名で書かれます。
設定の `my_class_aliases` にその呼び方を登録すると、自分のクラスとして扱われます。

**日付の食い違いは、採用したかどうかに関わらず必ず両方の日付と出典を表示します。**
黙って片方を選ぶと、取り違えたときに気づけないためです。

## 3. 書き込みの安全性

想定している運用は「パイプラインが自動で入れ、家族が手で整える」です。
つまり、**カレンダー上の予定はこちらの出力だけではありません。**

- **冪等**: 予定の識別子を `extendedProperties` に保存し、再実行しても重複登録しない
- **手編集の保護**: 書き込みのたびに、こちらが管理する項目の指紋を刻む。次回、
  現在の内容が指紋と合わなければ人が触ったということなので、更新せずに残して報告する
- **「変わった」の定義を1つにする**: 更新の要否判定と手編集の検出は同じ指紋から
  導く。別々の比較を持つと、片方が保護した予定をもう片方が書き換える
- **削除は既定でしない**: 抽出結果から消えた予定は「削除候補」として報告するだけ。
  `--prune` を明示したときだけ削除する。資料を一時的に退避しただけで予定が消えると困る
- **確信度で揺れた予定は削除しない**: しきい値を少し下回っただけの予定は資料に
  依然として載っている。消すと、実行のたびに登録と削除を繰り返すことになる

## 4. 抽出の不確かさ

LLMの出力をそのまま信じない、という前提で作っています。

- **確信度**: しきい値未満の予定は登録せず一覧表示のみ
- **重複候補**: 似ているが別物かもしれない予定は自動統合せず、候補として出す
- **期間の長すぎる予定**: 「9月中のどこか1日」のような日付の定まらない連絡が、
  期間全体にまたがる1件として抽出されることがある。カレンダー上で毎日表示され
  続けるので、`max_span_days` を超える終日イベントは確信度を下げて登録対象から外す
- **年度のずれ**: 本文に年が無い日付で、ファイル名の数字列(「250925」など)を年の
  根拠にしてしまうことがある。資料の配布日から学校の年度(4月始まり)を求め、
  ずれていれば確信度を下げる
- **補足情報**: 「9月7日の週」のような書き方を実施日に直すには時間割の知識が要るが、
  それは資料に書かれていない。設定の `extraction_notes` に自由文で前提を書くと、
  プロンプトの末尾に足される

## 5. 費用

抽出1回ごとに課金されるので、同じ資料を何度も送らない仕組みが要ります。

- **キャッシュ**: 本文のハッシュをキーに抽出結果を保存する
- **指紋**: キャッシュには「モデル+システムプロンプト+ツール定義+補足情報」の指紋も
  持たせ、一致しなければ作り直す。これが無いと、プロンプトを改善しても
  キャッシュ済みの資料には反映されず、修正が黙って無視される
- **実測**: 応答の `usage` を積み上げ、実行ごとの費用を表示する。応答の解析に
  失敗しても課金は発生するので、使用量は解析前に記録する
- **残高の目安**: 残高を返すAPIは無いので、Consoleで確認した値を基準に記録し、
  そこからの支出を差し引いて表示する

## 6. 個人情報の扱い

学校からの配布物には、子どもの氏名・クラス・学校名・教員名が含まれます。
これらがリポジトリに入らないよう、置き場所を分けています。

- `config.yaml`, `exclusions.yaml`, `secrets/`, `inbox/`, `.env` は **gitignore 済み**
- 追跡するのは `config.example.yaml` などの雛形だけで、値はすべて一般的な例
- コード中のコメントやテストの例にも、実在する学校名・コース名・行事名・教員名を
  書かない。断片的でも組み合わせると特定できるため

## 既知の限界

- **Classroom は手動**: API連携していないので、投稿本文をコピーして
  `inbox/manual/` に置く必要がある
- **抽出結果は毎回わずかに揺れる**: 同じ資料から前回取れた予定が取れないことがある。
  削除候補として報告されるので気づけるが、自動では解決しない
- **`--prune` が見るのは取得した範囲だけ**: 同期対象の最も古い予定から遡った窓の
  外にある予定は、削除候補に上がらない
- **表形式の資料に弱い**: 行と列で意味が決まる表(教科ごとの授業予定表など)は、
  そのままLLMに渡すと精度も費用も見合わない。列を決め打ちで読む前処理が要る
